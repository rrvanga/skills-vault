# DRM / display / GPU diagnostics (Linux, Arch)

## When to use
External display stuck at 640x480 (or a mode list that makes no sense), monitor "not detected" / wrong resolution, nvidia-smi or CUDA apps failing with driver/library mismatch, GPU-role questions ("which GPU drives what").

## This box's topology (Lenovo 229f / X1E Gen 2)
- PCI 00:02.0 Intel UHD 630 (i915) = card1; owns eDP-1 (internal panel) ONLY.
- PCI 01:00.0 NVIDIA GTX 1650 Mobile Max-Q (open module) = card0; owns DP-1, DP-2, HDMI-A-1. **No mux** — external connectors are wired to the dGPU, so an external display is physically NVIDIA-only; iGPU cannot drive externals; BIOS "Integrated" mode kills externals AND GPU compute.
- Standing GPU-role directive: NVIDIA only for local LLM; iGPU for displays/desktop.
- Probe outputs are long on this box → route to /tmp files and read back with read_file (see linux-system-audit Pitfalls).

## Probe chain (all read-only)
1. Topology: `ls -l /dev/dri/by-path/` (card0/1 <-> PCI), `cat /sys/class/drm/card0-*/status`, `cat /sys/class/drm/card0-*/modes` (the modes list is EDID-derived).
2. EDID: `dd if=/sys/class/drm/card0-<conn>/edid of=/tmp/x.edid bs=128 count=2` then `edid-decode /tmp/x.edid` (edid-decode ships in an Arch package; no parse-edid needed).
3. State: `kscreen-doctor -o` with `XDG_RUNTIME_DIR` + `WAYLAND_DISPLAY=wayland-0` set; journal: grep kwin/drm/EDID around the hotplug timestamp (`journalctl -b --no-pager`).
4. Driver alignment: `uname -r` vs `pacman -Q linux`; `lsmod | grep nvidia`; `nvidia-smi`; `pacman -Qu` (empty = fully updated).

## "Display turned off and on": blip vs idle-lock — triage FIRST
Before touching any config, decide which of two very different events the user actually saw:
- **Re-sync blip** — dark for ≤ ~1 s, then back: no journal line, DPMS On, KWin layout unchanged → TMDS/PHY-level signal loss at the current mode's pixel clock. Diagnose with the EDID link-budget decode below.
- **Stuck dark for minutes** — all outputs `dpms=Off`: the session idled out and locked. Prove it with `loginctl show-session <active-N> -p LockedHint -p IdleHint` (LockedHint=yes) plus `qdbus6 org.kde.screensaver /ScreenSaver GetActive`. This is normal KDE behavior (idle → blank → lock), not the bug under investigation; wake = user keypress + password. `SimulateUserActivity` clears idle but does NOT unlock a locked session — never promise the agent can raise it unaided.

## NVIDIA dummy/fallback EDID — the 640x480 signature
Signs: connected but ONLY 640x480 modes; EDID dump is 128 bytes; edid-decode shows Manufacturer **NVD** (NVIDIA's own PnP ID), Model 0, Year 1990, established timings 640x480 only, all detailed-timing descriptors EMPTY, checksum valid. This is NVIDIA's built-in fallback blob substituted because the monitor's real EDID never arrived over the link (cable/connector/dock DDC fault) — NOT a driver bug and NOT fixable in config. The fix is physical: reseat/replug the cable or power-cycle the monitor (direct cable beats a dock/dongle). Verify by re-dumping the EDID after the retest — a real monitor decodes with its own manufacturer and at least one detailed timing.

## NVIDIA 'Driver/library version mismatch' = reboot pending, not a broken install
nvidia-smi fails with `Failed to initialize NVML: Driver/library version mismatch` while userspace packages look fine → the running kernel still has an older nvidia module loaded in memory than the userspace libs on disk. Prove it: module version in memory (lsmod / boot journal) < installed `nvidia-open`; `uname -r` older than installed `linux`; `pacman -Qu` EMPTY; the installed kernel's modules exist (`ls /usr/lib/modules/<installed-ver>/extramodules/ | grep nvidia`) and `/boot/vmlinuz-linux` + initramfs were rebuilt. Everything on disk is consistent — the ONLY missing step is a reboot; do NOT reinstall or blacklist. Re-verify with nvidia-smi after boot.
- Same signature explains: CUDA/llama-server failing to initialize right after an update (identical NVML mismatch) and new displays connecting with the fallback blob — check reboot-pending before blaming anything else.
- Journal signature from any NVML-poking client while it runs: `NVRM: API mismatch: the client 'nvidia-smi' (pid N)… has the version X, but this kernel module has Y`.
- Triage reads: `cat /proc/driver/nvidia/version` (module loaded in memory) vs `modinfo nvidia | grep ^version` (module on disk) vs `nvidia-smi` (userspace libs). On-disk == userspace != loaded, confirmed against `grep nvidia /var/log/pacman.log` = the package was upgraded mid-run; the loaded module simply lags until reboot.
- Plain reboot suffices only if the module is NOT in the initramfs: `lsinitcpio /boot/initramfs-linux.img | grep nvidia` — firmware + modprobe.d entries alone mean it loads from /usr/lib/modules at boot (the reboot picks up the new one); a real `nvidia.ko` inside the initrd needs `mkinitcpio -P` first.
- Pitfall: `/sys/module/nvidia_drm/parameters/*` are 0400 root (Permission denied for the user) — read module facts from lsmod/journal/nvidia-smi, not those param files.

## EDID link budget: why a mode drops out, and which rung to fall to
A monitor that intermittently blanks-and-resyncs with zero software trace is exceeding the link's real TMDS capability. Quantify before changing any mode:
1. Real EDID: `dd if=/sys/class/drm/card0-<conn>/edid of=/tmp/x.edid bs=128 count=2` then `edid-decode /tmp/x.edid`.
2. Pixel clocks: read each advertised mode's pixel clock from the CTA-861 DTDs. Declared ceiling: HDMI 1.4 VSDB (tag 3, OUI `00-0C-03`) payload byte 6 (0-indexed) = `Max_TMDS_Clock` in **5 MHz units** (0x38 → 280 MHz). HDMI 2.0 is declared by an HDMI Forum VSDB (extended tag 0x01) whose 16-bit max-TMDS-character-rate field (also 5 MHz units) caps the absolute ceiling at 600 MHz.
3. Compare the mode's pixel clock against BOTH the declared Max_TMDS_Clock and the 600 MHz ceiling. A monitor can advertise modes in its own DTD list that its own vendor block declares out of range (this box: 144 Hz = 581.6 MHz vs declared 280 MHz, ~97% of the hard ceiling) — advertising is not a promise the TMDS link can hold the mode. ≥ ~90% of the 600 MHz ceiling = marginal regime → drop one rung (~80%, e.g. 1440p@120 = 479.8 MHz) and re-watch before touching cables.
- Decode pitfall: VSDB OUI bytes are little-endian — payload starts `03 0C 00` for OUI `00-0C-03`; a naive reversed compare silently fails to identify the block.

## KWin output config: monitor "keeps turning on and off", wrong scale/position (Plasma Wayland)
`~/.config/kwinoutputconfig.json` is a KConfig-JSON file KWin owns: top-level array of groups `{"name":"outputs","data":[...]}` and `{"name":"setups","data":[...]}`. `outputs` = one entry per remembered monitor (connectorName, edidIdentifier, uuid, mode{flags,width,height,refreshRate **in milli-Hz**}, scale, brightness, colorPowerTradeoff, allowDdcCi…). `setups` = one entry per remembered arrangement: `{lidClosed, outputs:[{enabled, outputIndex, position{x,y}, priority, replicationSource}]}`, where **outputIndex indexes the `outputs` array**, and there is normally one setup per (lid state, connected-output set).

Two failure modes that look like flapping:
- **Duplicate entries for one connector with different edidIdentifier/uuid** (an old monitor replaced on the same port: `HDMI-A-1 DEL …` beside `HDMI-A-1 ACR …`) plus dead monitor entries (disconnected DP-*) → several setups per lid state, and the wrong one can apply on lid/hotplug, blanking or misframing the external. Ghosts are usually inert (KWin matches stored outputs by identity, not connector name) but they are candidates.
- **`brightness` < 1.0 with `colorPowerTradeoff: PreferEfficiency`** = KDE quietly dimming an external over DDC/CI (0.41 = 41%!). Set `brightness: 1.0`, `colorPowerTradeoff: "PreferAccuracy"`, `allowSdrSoftwareBrightness: false` unless the user wants KDE dimming it.

Fixing it:
1. Read live state first: `kscreen-doctor -o` (needs `XDG_RUNTIME_DIR=/run/user/<uid>` + `WAYLAND_DISPLAY=wayland-0`). Note the starred mode, Geometry, Scale, priority. Primary is derived from position — **there is no `kscreen-doctor … priority.N` knob**; the output at `position.0,0` becomes primary.
2. Repair the current session live: e.g. `kscreen-doctor output.HDMI-A-1.mode.2560x1440@120 output.HDMI-A-1.scale.1 output.HDMI-A-1.position.0,0 output.HDMI-A-1.brightness.100 output.eDP-1.disable` (`.mode.WxH@R`, `.brightness.` = 0-100, `.enable`/`.disable`). Each apply makes KWin *upsert* the setup for the **current** lid state (`/proc/acpi/button/lid/*/state`) — a restart-free way to repair one lid state at a time.
3. Rewrite the file with only outputs that exist (one per physical connector) and one setup per lid state. **Bind the group objects, not the data**: `groups = {g["name"]: g for g in doc}` then `groups["outputs"]["data"] = [...]`. Using `{g["name"]: g["data"] for g in doc}` gives copies — assignments silently no-op and you rewrite the stale content.
4. **KWin reads this file ONLY at session start** and keeps its own in-memory copy; `qdbus org.kde.KWin /KWin reconfigure` does NOT reload it. Prove it by forcing a save (any no-op `kscreen-doctor` apply) and diffing — the old table returns verbatim. So the file change needs logout/login or reboot.
5. **Any lid toggle makes KWin re-dump its entire in-memory table over the file** — pair `journalctl` lines `systemd-logind[…]: Lid closed.` / `Lid opened.` against the file mtime and it lands on the lid event (writing on lid-*open*). It is not a timer or a DPMS/blanking side effect: an idle 60 s watch shows zero writes. So a staged file survives only until the next lid event — and **it will not survive a reboot either**: KWin saves its in-memory table when the session ends and starts, so the staged file is overwritten before the next KWin reads it (a staged 2-monitor file came back as the identical 5-monitor/8-layout ghost table, mtime 3 s after `kwin_wayland` started). Never tell the user a reboot will clean the file. Purging stale entries needs KWin to start with **no** config at all (delete it from a TTY while logged out so KWin regenerates a fresh table from the connected monitors), or a login-time hook that provably runs before `kwin_wayland` starts — verify the hook point, `~/.config/plasma-workspace/env/*.sh` is not guaranteed to be sourced.

6. **Check whether the stale entries actually hurt before chasing that — usually they do not.** KWin matches stored setups to current outputs by output *identity* (EDID/uuid), not connector name: with an 8-layout table containing ghost `HDMI-A-1 DEL` / `DP-3` / `DP-1` entries it still applied the external-only layout whose competing sibling used the same connector name with a different EDID. Tell the user the ghosts are inert rather than pursuing a cosmetic cleanup.

7. The same lid journal line carries `org_kde_powerdevil: Lid action was suppressed because an external monitor is present` — clamshell-with-external correctly does not suspend; cite it to reassure instead of hunting a suspend bug.
- `systemctl reboot` is on the agent platform's **hardline blocklist**; never route around it — hand the user the command.
- "Use only the external monitor whenever it is connected" = encode **both** lid states as `external ON @0,0 p1 | internal off`. With the external absent, no setup matches and KWin generates its normal default, so the laptop panel comes up. Do NOT add an internal-only setup — a stored setup that omits a connected display is exactly what turns it off.
## Watcher design for intermittent display events
- Log FULL before/after snapshots (per-connector `/sys/class/drm/card*-<conn>` `status`+`dpms`+`enabled`, the kscreen-doctor lines you filter, and screensaver `GetActive`) on every change — a layout HASH records that something changed but not what, and the signature (output disabled vs geometry shift vs lock) is exactly what separates real instability from KWin's own mode-set transition. One coarse generation costs you one incident.
- A deliberate mode apply (`kscreen-doctor output.*.mode.*`) legitimately produces a transition window of tens of seconds of layout churn on NVIDIA — verify the final state instead of declaring instability from a hash change inside that window; the full-snapshot watcher settles it afterwards.
- Stop a background watcher by EXACT match: `pgrep -fx 'python3 /abs/path/script.py'` then `kill <pid>`. `pkill -f <script>` also matches your own shell command line (it contains the pattern) and SIGTERMs your terminal call mid-run (exit -15).
- Keep repair/watcher scripts under `~/.local/state/hermes/display/` — /tmp is wiped at boot and KWin can still clobber `~/.config` files, so the state-dir copy is the durable reference.

Remaining flicker levers, in order: quantify the first via the EDID link-budget decode above (1440p@144 = 581.6 MHz ≈ 97% of the 600 MHz ceiling — marginal → drop to 120 Hz); then disable DDC/CI brightness control (PowerDevil polls the HDMI i2c bus on a ~10 s cadence, visible as DRM `change` uevents naming `/dev/i2c-*`); then idle DPMS blanking (screensaver) — that shows as `enabled=disabled` + `dpms=Off` on **all** outputs at once, i.e. blanking, not a layout change.
